## Context

切换控制器的静默期来自 controller_manager 的执行顺序（jazzy）：

| 步骤 | 位置 | 效果 |
| --- | --- | --- |
| 服务线程 `prepare_command_mode_switch()` | `controller_manager.cpp:2369` | 仅校验 |
| 服务线程置 `do_switch = true` | `:2387` | 开始切换 |
| RT `update()` 按 `skip_cycle()` 跳过 activate/deactivate 列表中的控制器 | `:3414`、`controller_manager.hpp:744-751` | **新旧控制器都不再写命令** |
| RT 在 `update()` 末尾置 `ready_to_switch` | `:3580-3588` | 通知服务线程 |
| 服务线程 `manage_switch()`：`perform_command_mode_switch()` → deactivate → activate | `:2408-2424`、`:3315-3368` | 门在其中第一步可以开启；`on_activate` 可能很慢 |

本插件每拍 `ResetCommands()`，所以静默期内每拍都判定为"已绑定模式但未写命令"。

## Goals / Non-Goals

**Goals:**

- 静默期内不再把"本周期无人写命令"报成非法命令。
- 首帧命令到达后立刻恢复既有语义；改动面最小（每关节一个布尔、判定只加在 `write()` 一处）。
- 不合成任何命令，不引入新参数、接口或服务。

**Non-Goals:**

- 超时上报与计数（用户明确要求"一直等待"）：代价见 Risks。
- 门内下发保持命令（需要 kp/kd/current 缺省值来源，且与 `openspec/project.md` 的"不得以缓存值、零值或
  推断模式填补不完整命令"冲突）。
- 只在 `prepare` 开门（不足，见决策 3）；消除静默期之前那一拍旧模式日志（见 Risks）。
- 控制器 `on_activate` 减重（属 `ec_slave_arm_controller` 的独立变更）。

## Decisions

### 1. 门是一个实例级布尔成员，放在 `EcJointHardware` 上

按用户要求不做每关节状态：本包的一个硬件实例对应一组设备（主臂 / 从臂 / 左右灵巧手），同一时刻只由一个
控制器驱动其中的全部关节，因此"本实例刚发生过切换"就足以描述需要静默的范围。代价见 Risks 第 1 条。

### 2. 判据 = "每个已认领关节都有命令槽被写入"

按用户要求：只要有一个已认领的关节本周期没写命令，就整批继续跳过，连已经写了命令的关节也不派发——这样
切换期间不会对任何关节产生非法命令日志。命令槽每拍末被 ResetCommands() 重置为 `NaN`，所以"任一槽非 `NaN`"
等价于"该关节本拍写过命令"。判定不查模式-接口映射、不区分必填接口，写了一半的非法命令同样算"已写"，随后
由既有分支记录错误。

未绑定模式的关节 MUST NOT 参与判定：它们永远不会有命令，若按字面把"没写"算上，整实例会被永久静默。

### 3. 开门必须同时发生在 `perform`（决定性）与 `prepare`（锦上添花）

`prepare` 与 `do_switch = true` 在同一次 service 回调里、间隔微秒级；这期间只要发生一次 RT `write()`，
旧控制器仍在写命令，会把刚开启的门关掉，随后整段静默期内门是关闭的——刷屏原样出现。`perform_command_mode_switch()`
在静默期内部被调用，在那里开门才是决定性的。提前在 `prepare` 开一次可以额外省掉静默期之前那一拍日志。

开门不区分"模式是否变化"：门是"本实例刚发生过切换"，因此同模式换控制器也覆盖（无需额外的认领判定）。

### 4. 门开时整批跳过，先判"是否所有已认领关节都写了"

```cpp
if (awaiting_first_command_) {
  if (!AllClaimedJointsHaveCommands()) {
    return finish(OK);                 // 还有已认领关节没写：整批跳过（命令槽照旧复位）
  }
  awaiting_first_command_ = false;     // 都已写入：关门，本周期照常派发
}
for (auto& joint : joints_) { /* 既有逐关节派发，一行不改 */ }
```

先判"是否都写了"的作用：只有全部已认领关节都写了才派发，切换期间不会出现"部分关节已派发、部分关节记
非法命令错误"的混合状态。`finish()` 复用既有 lambda，保证跳过的周期同样复位命令槽。

### 5. 未绑定模式的关节不参与判定

`switch_controllers` 只带 `--deactivate`（或切换后没有任何关节保留认领）时，全部模式都是
`ModeDefinition::None`，判定为空真 ⇒ 门当拍关闭，未绑定模式那条"零扭矩 PVT 维持底层反馈请求链路"的既有
行为照常执行，不会因为没有控制器写命令而被永久跳过。这也是"未绑定模式不参与判定"必须写进规范的原因：
否则整实例会被永久静默。

### 6. `on_configure()` 清门

重配后残留门状态，而重配期间控制器不写命令；因为**没有超时**，该关节会永久静默。清门与 `joint.ptr.reset()`
同处执行。

### 7. 无超时是刻意的取舍

用户要求"控制器一直不更新命令就一直等待"。收益是切换窗口内绝不刷屏；代价是"控制器激活后从不写命令"
这类真实故障不再有任何日志（见 Risks）。日后要恢复诊断能力，最小增量是"门内每 N 拍记一次 WARN"，
不影响派发逻辑。

## Risks / Trade-offs

- **整实例永久静默**：只要有一个已认领的关节长期不写命令（`update_rate` 低于 controller_manager 频率、
  `update()` 提前 return、或写全 `NaN`），本实例**全部关节**都会持续被跳过且不再产生任何错误日志——这是
  "有一个没写就整批跳过 + 不设超时"的直接后果，是本次刻意接受的取舍，必须写进 README。
- **门是实例级的**：同一实例内若出现"只有部分关节被切换、其余关节仍由另一个控制器驱动"的拓扑，任一未写
  命中的关节（含未切换但仍在写命令的关节）都会让门当拍关闭，被切的那部分关节随后回到既有错误语义——即
  刷屏回归。本包当前部署是一个实例一个控制器（主臂 / 从臂 / 左右手各自独立实例），不存在该拓扑；若以后
  出现，需要改回按关节维护门状态。
- **每次切换仍残留 1~2 条旧模式 ERROR**：`do_switch = true` 紧跟 `prepare`，而 `perform` 最早在其后一拍执行；
  那一拍旧模式 + 全 `NaN` 且门未开。要彻底消除需保证 `prepare` 与 `do_switch` 之间不发生 `write()`，不可靠。
- **门内该关节无命令下发**：时长 = 切换耗时（当前实现含 `ArmControllerImpl` 构造，数十毫秒量级）。电机反馈
  是否依赖命令帧属 `openspec/project.md` 标注的 UNKNOWN，需实机确认；若确认依赖，需回到"门内下发保持命令"
  的方案重新裁决。
- **误用风险**：判定若把未绑定模式的关节也算作"没写"，整实例会被永久静默；若在门内不判"是否都写了"，
  就会出现部分派发、部分记错的混合状态。两点都必须有回归用例。
